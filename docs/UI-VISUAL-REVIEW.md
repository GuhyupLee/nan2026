# UI/UX · 에셋 · 그래픽 · 이펙트 품질 보고서

작성 시점 HEAD: `995c310`. 검토 방법: 소스 정독(ui.css 4,385줄 전수, render/ 전 모듈,
에셋 바이너리 파싱) + **실행 중인 게임의 브라우저 실측**(computed style, WCAG 대비율
계산, 네트워크 계측). 로직 버그는 별도 검토에서 다뤘고, 이 문서는 보이는 것·들리는
것·만져지는 것의 품질만 다룬다.

## 종합 진단 — 세 문장 요약

1. **폰트가 실제로 존재하지 않는 타이포 시스템** — Pretendard·Noto Serif KR을 전제로
   웨이트 23종을 조율해 놓았지만 웹폰트를 하나도 싣지 않아, 대부분의 기기에서
   맑은 고딕으로 렌더된다. 이 하나가 UI 인상 전체를 결정한다.
2. **만들어 놓고 배선 안 된 타격감 장치가 유독 많다** — 히트스톱 예산, bloomBoost,
   무기 궤적 리본, onImpact 파티클 훅, crit 스타일이 전부 코드에 존재하지만 화면에
   한 번도 나오지 않는다. 화면의 타격감이 코드 역량 대비 현저히 낮은 이유다.
3. **에셋 40MB 중 절반 이상이 군살** — VRM 안에 렌더되지 않는 썸네일 4.8MB, 참조
   0건의 사장 에셋 1.96MB, dist 이중 복제 44MB. 정적 호스팅 게임에서 첫 로드가
   무겁다.

## 1. 타이포그래피

### 1-1. 한글 웹폰트 미탑재 (치명적)

- `index.html:75`가 `"Pretendard Variable", Pretendard, "Noto Sans KR", "Segoe UI"`를,
  `ui.css:2863` 등이 `'Noto Serif KR', 'Nanum Myeongjo', 'Batang', serif`를 선언하지만
  저장소 전체에 `@font-face`·woff2·폰트 링크가 **0건**이다. 실행 중 `document.fonts`도
  빈 집합으로 실측 확인.
- 결과: Windows에서 Segoe UI(라틴)+맑은 고딕(한글) 혼합. 메인메뉴·캐릭터 선택의
  "편집 명조" 정체성(`ui.css:2863, 3093, 3264`)은 명조 미설치 기기에서 바탕체로 무너진다.
- 부수: `font-weight` 고유값 **23종**(500~850 미세 단계)은 가변 폰트 전제 설계다.
  맑은 고딕은 400/700 두 단계뿐이라 이 조율 전부가 뭉개진다.
- **수정**: Pretendard Variable + Noto Serif KR 서브셋 woff2 self-host,
  `font-display: swap` + `<link rel="preload">`. 이후 웨이트를 4~5단계 토큰으로 정리.

### 1-2. px 하한 없는 구세대 텍스트 — 720p에서 판독 불가

루트 스케일 `--ui-scale: clamp(12px, …)`(`index.html:51`) 때문에 **1280×720에서

## 3. 레이아웃 · 반응형 · 터치

**잘된 것부터**: safe-area(`--ui-safe-*` + `env()`) 전 화면 일관, `@media (pointer:
coarse)`에서 스킬 슬롯 48px/소환사 44px 승격(`ui.css:2494-2506`), 메뉴 버튼
min-height 48px, 319px 초소형 대응까지 — 인디 규모에서 모범적.

- **3-1. 마우스 환경 터치 타깃** — 포인터 fine에서 스킬 슬롯 39×39px, D/F
  32×32px(실측). 클릭 대상이라기보다 표시물이라 치명적이진 않으나 호버 툴팁
  타깃으로는 작다.
- **3-2. 전투 중 터치 툴팁 오발** — `skillbar.ts:220`이 터치 pointerdown마다 툴팁을
  띄워, **스킬을 누를 때마다 21.5rem 폭 툴팁이 1.8초간 화면을 가린다**
  (`ui.css:3966`, `skillbar.ts:478`). 전투 중에는 롱프레스에만 열도록 분리.
- **3-3. 볼륨 슬라이더** 높이 28px, 썸 18×24px — 터치 44px 미달(`ui.css:1798, 1813`).
- **3-4. XP바 두께 3.5px**(`ui.css:157`, 실측 3px) — 사실상 보이지 않는다. 뱀서류에서
  XP 게이지는 "다음 선택까지 얼마나"라는 핵심 기대감 장치다. 최소 6~8px + 획득
  순간 펄스 권장.
- **3-5. 스킬바 중앙 배치** — 375px 양손 그립에서 엄지 이동 거리가 길다. 모바일은
  우하단 부채꼴 배치 검토.

## 4. 정보 위계 · UX 흐름

**골격은 견고**: HP는 캐릭터 머리 위(시선 이동 최소), 타이머 상단 중앙 + 마지막
30초 점멸, 보스바 + 페이즈 텍스트, 쿨다운 숫자+원형 게이지+완료 플래시.

- **4-1. 레벨업 카드의 랭크 시각화 실패** — `levelup.ts:332`가 `data-rank`를
  설정하지만 **CSS에 `[data-rank]` 셀렉터가 없다**(죽은 데이터). family 강조색
  `--family-accent`(`ui.css:4140`)는 1px border-bottom에만 적용되는데 그 위를 2px
  `::after` 스트립이 덮어 **보이지 않는다**. 랭크 핍(●●○)을 카드 상단에 노출하고
  family 색을 스트립 자체에 적용할 것. 각성/융합 카드의 골드 전환은 성공적.
- **4-2. LV 이중 표기** — 플로팅바 배지(`hud.ts:52`)와 run-info(`hud.ts:73`) 중복.
  한쪽 제거로 상단 밀도 완화.
- **4-3. 메인메뉴 01/02/03 번호의 허위 어포던스** — 숫자 키 입력이 구현돼 있지
  않다(`mainmenu.ts:75-95`). 연결하거나 장식임을 명확히.
- **4-4. 네이밍 드리프트** — UI는 "루멘"(빛의 마법사), 코드 주석·에셋은
  "일현"(`ilhyeon.vrm`), 궁극기 이름도 "일현". 의도(캐릭터=루멘, 궁극기=일현)라면
  코드 주석·파일명과 문서를 정합시키고, 아니라면 한쪽으로 통일할 것.

## 6. 디자인 시스템 일관성

정량 증거: 고유 font-size **89종**, font-weight **23종**, duration **17종**,
스페이싱 임의값(0.42/0.44/0.46/0.48rem…).

- **6-1. 한 파일 안의 두 세대** — `ui.css` 4,385줄에 메인메뉴/캐릭터선택이 전반부와
  "editorial v2"(2744~)에서 이중 정의. `.lvcard p { display:none }`(`ui.css:2665`)를
  후반이 다시 뒤집는 데드 룰 존재. 구세대 블록 삭제 + `:root` 토큰(타입 5단계,
  4pt 그리드, duration 3종)으로 통합.
- **6-2. 스코어보드만 다른 언어** — `.scoreboard .total`이 radius 0.6rem + 독자
  청회색 팔레트(`ui.css:2024, 2079`)로, 전체의 "직각 + 하드 오프셋 섀도" 문법을
  깬다. 승패 직후 가장 오래 응시하는 화면이라 이질감이 두드러진다.
- **6-3. 렌더 팔레트 드리프트** — 시안 3종(`0x4dd0ff`/`0x56c7e8`/`0x62d9f7`), 크림슨
  2종(`0xff5a6e`/`0xff6578`)이 5개 파일에 산재. `src/render/palette.ts` 단일화 권장.
- **6-4. 위험색 의미 충돌** — 텔레그래프 해칭 `uDanger 0xff4a2e`(`skillfx.ts:1125`)가
  **플레이어 스킬 예고**에 쓰인다(world.blasts는 전부 플레이어 소유). 적 스킬이
  추가되는 순간 색 언어가 무너진다. 규칙 제안: 플레이어 예고 = 클래스색 윤곽
  무채움 / 적 예고 = 적색 해칭 전용.

## 7. 에셋 파이프라인

### 7-1. VRM 40MB — 압축 전무 + 렌더 안 되는 썸네일 4.8MB (상)

- `vrm-rig.ts:414-417` — GLTFLoader에 meshopt/draco/KTX2 미설정. 바이너리 파싱 실측:
  - `ilhyeon.vrm` 22.9MB = PNG 32장 14.1MB 포함, 그중 **Thumbnail 3.34MB는 게임에서
    절대 렌더되지 않는 프리뷰**
  - `wola.vrm` 18.4MB = PNG 30장 10.0MB, Thumbnail 1.49MB
- 썸네일 2장 제거만으로 **-4.8MB(12%)**. VRoid 재수출(텍스처 2048→1024 + 아틀라스)로
  40MB → 12~16MB가 현실적. 일반 gltf-transform 최적화는 `VRMC_*` 확장을 깨뜨릴 수
  있으니 VRM 전용 경로로.
- `tools/optimize-art.ts`는 PNG→WebP만 다루고 모델은 파이프라인 밖 — "생성부터
  최적화까지 재현" 주장(7-9행)에 모델이 빠져 있다.

### 7-2. 죽은 에셋 1.96MB가 배포에 포함 (상)

| 파일 | 크기 | 상태 |
|---|---|---|
| `public/og.png` | 1.04MB | 참조 0건 (`og-v2.png`만 사용) |
| `public/art/main-menu-keyart.webp` | 282KB | 참조 0건 (v2만 사용) |
| `public/art/magic-girl-hero.webp` 외 3장 | 642KB | 참조 0건 (portrait-v2만 사용) |

`-v2` 수동 버저닝이 구버전을 리포·배포에 계속 남기는 뿌리 원인.

### 7-3. dist 88MB — client/ 전체 이중 복제 (상)

`tools/site-build.mjs:12-18`이 dist 전체(모델 40MB 포함)를 `dist/client/`로 복제.
GH Pages에 dist 루트를 올리면 모든 에셋이 두 경로로 이중 배포된다. client/를 별도
산출 디렉터리로 빼거나 배포에서 제외.

### 7-4. 로딩 UX (중)

- 잘된 것: 메뉴 중 백그라운드 프리로드, 200ms 내 완료 시 로딩 화면 생략, 모바일
  VRM 스킵.
- 부족: 23MB를 기다리는 로딩 화면이 **텍스트 한 줄**(`main.ts:426`), 진행률 없음.
  fetch reader로 바이트 진행률을 받아 index.html의 기존 `.bar`를 채우는 것이 저비용.
- 실측: 메인 메뉴 진입 시점에 **두 캐릭터 VRM 41MB를 전량 다운로드**한다(선택
  전에). 프리로드 자체는 좋으나 7-1 다이어트가 전제.

## 8. 렌더링 품질 · 성능

**정석인 부분**: 선형 HDR → Bloom → Grade → OutputPass(ACES+sRGB 마지막) 순서,
커스텀 셰이더의 tonemapping 자기무력화, 그림자 단일 광원 2048/플레이어 추종 타이트
절두체, 픽셀비 상한, low 품질의 CSS 해상도 컴포저.

- **8-1. FXAA가 톤매핑 전 선형 HDR에서 동작**(`post.ts:179-183`) — FXAA는 지각
  루마 전제라 발광 경계 AA 품질이 떨어진다. 가산 이펙트가 주인공인 게임이라
  체감 있음. **OutputPass 뒤로 이동**(또는 WebGL2 컴포저 타겟 `samples: 4` MSAA).
- **8-2. `antialias: true` 낭비**(`renderer.ts:131`) — 실제 씬은 컴포저의 비MSAA
  타겟에 그려져 기본 프레임버퍼 MSAA는 메모리만 소비.
- **8-3. 데미지 숫자가 이펙트에 씻긴다** — 숫자 renderOrder 20(`impact.ts:447`) <
  빔 22·플레어 23(`skillfx.ts:1144, 1174`). 가장 밝은 타격 순간에 숫자가 가산광에
  묻힌다. **renderOrder ≥ 30으로**.
- **8-4. FPS 기반 자동 품질 강등 부재** — 'off' 경로는 있으나 선택 조건이 화면
  크기/포인터뿐. 내장 GPU 대화면 데스크톱이 high 고정.

## 9. VFX 커버리지 — 이벤트별 지도와 타격감 체인

| 이벤트 | 현재 | 판정 |
|---|---|---|
| QWER 8종 시전 | 클래스별 개별 연출 | 양호 |
| 원거리 평타 | 빔+머즐+보주 킥 | 양호 |
| 근접 평타 | 참격 호 (무기 리본은 미배선) | 절반 |
| 적 피격/사망 | 플래시 / 팝 껍데기만, **파티클 모듈 자체 부재** | 약함 |

### 9-1. 최우선: 승리/패배 연출이 한 프레임 만에 잘린다 (상)

sim이 보스 사망 틱에 `outcome='victory'`를 세우면 `main.ts:214-237`이 **같은
프레임에** `activeRun=false`로 렌더를 멈추고 오버레이를 띄운다. 걸어 놓은 1.1초
흔들림 + 0.12초 히트스톱 + 0.6초 백색 플래시(`renderer.ts:464-467`)는 1프레임만
보이고 소멸. 패배도 동일 — "사망의 순간"이 없다.
**수정**: outcome 확정 후 0.8~1.2초 연출 유예(렌더 유지, 입력만 차단, 선택적
슬로모션) 뒤 오버레이 페이드인. **5분 런의 마지막 인상을 이 하나가 결정한다.**

### 9-2. 파티클 계층 부재 — onImpact 훅 4곳이 전부 허공 (상)

`skillfx.ts` 4곳(1340, 1539, 1611, 1660)이 `hooks.onImpact?.()`로 타격 지점을
넘기지만 `renderer.ts:162-164`는 `onShake`만 배선. **스파크·파편 입자가 게임 전체에
0개.** 소켓이 이미 있으니 InstancedMesh 입자 풀 1레이어로 즉시 채울 수 있다.

### 9-3. 사장된 타격감 장치 (중)

- `requestHitstop` 실사용 1곳(그마저 9-1로 안 보임) — impact.ts의 히트스톱 예산
  시스템(54-55행)이 실전 사용 0
- `PostFx.setBloomBoost`(`post.ts:254`) 호출 0건 — 궁극기 화면 발광 사장
- `ImpactFx.flashEnemy`(`impact.ts:628-649`) 호출 0건
- damage 스타일 `'crit'`/`'xp'`(`impact.ts:115`) 미사용 — 정예·보스 피해에 전용 권장

**이펙트 구현 품질 자체는 상위권** — 7드로우콜 고정 인스턴싱, 프레임 할당 0,
NaN 방어, 시뮬/벽시계 이중 시계 분리. 문제는 품질이 아니라 **배선**이다.
